Sổ Tay Kinh Nghiệm Kỹ Thuật

Nơi lưu giữ lịch sử thay đổi, những sai lầm kiến trúc, các quyết định đánh đổi (Trade-offs) và bài học xương máu xuyên suốt quá trình xây dựng dự án Parental Control.

Kế Hoạch Hành Động (MVP V1.0)

Mục tiêu: Bịt kín 3 tử huyệt lớn nhất trước khi phát triển thêm tính năng mới.

1

Vá lỗ hổng Định danh (API Spoofing Prevention)

Sinh Device_Secret_Token lưu bằng Windows DPAPI/Credential Manager. Bắt buộc kiểm tra (Middleware) trên FastAPI Backend để loại bỏ hoàn toàn việc dùng Postman giả mạo tín hiệu.

2

Cảnh báo Telegram Phân loại (Smart Alerts)

Agent bắt sự kiện Shutdown/Sleep để gửi "Tạm biệt" hợp lệ. Backend bắn Telegram cảnh báo ngay lập tức nếu Agent mất kết nối mà không có lời từ biệt (bị Kill qua Task Manager).

3

Hàng đợi Offline (Store and Forward Queue)

Ghi log (app, web) vào SQLite nội bộ khi rớt mạng. Bulk Upload (Batching) lên Server khi có mạng lại để triệt tiêu mánh khóe "rút cáp Wi-Fi để chơi game".

Lịch Sử Phân Tích & Bài Học Xương Máu

Bài học 1: Sự ngây thơ của "Device Name" và File .env

Sai lầm: Dùng tên máy tính (chuỗi) để định danh, hoặc dùng Secret Token nhưng lưu thẳng vào file .env ở dạng plain-text.

Giác ngộ: Trẻ em là những kẻ tấn công (Adversaries) sống ngay bên trong hệ thống. File .env là vô dụng trước một user biết dùng Notepad. Việc giả mạo định danh sẽ phá nát hoàn toàn "Sự tin cậy" (Trust) của phụ huynh.

Giải pháp chốt: Bắt buộc dùng Windows DPAPI. Dữ liệu được mã hóa gắn với tài khoản hệ thống, nâng rào cản từ "biết đọc chữ" lên "biết hack hệ điều hành".

Bài học 2: Bẫy hoàn hảo của "Windows Service quyền SYSTEM"

Sai lầm: Muốn tạo ra một "Pháo đài" không thể bị tắt, đòi hỏi tốn 2-4 tuần bọc Python thành Windows Service quyền SYSTEM.

Giác ngộ: Cố gắng viết Python để chống lại quyền Administrator trên Windows là một nỗ lực viển vông. Quan trọng hơn, chi phí triển khai quá cao, rủi ro bị Antivirus chém nhầm (False Positive) sẽ giết chết dự án trước khi nó ra mắt (Over-engineering).

Giải pháp chốt: Áp dụng lộ trình MVP 80/20. Chạy ẩn ở User-mode, dùng cơ chế Watchdog kép để chống các thao tác tắt bằng chuột thông thường. Chấp nhận bị kill bởi những đứa trẻ cực giỏi IT, nhưng dùng Backend để phát hiện và báo cáo.

Bài học 3: Nghệ thuật chống "Alert Fatigue" (Mệt mỏi cảnh báo)

Sai lầm: Cứ hễ mất kết nối (Offline) là báo Telegram ngay cho phụ huynh, dẫn đến spam tin nhắn khi máy Sleep, Shutdown bình thường hoặc Wi-Fi chập chờn.

Giác ngộ: Nếu điện thoại kêu quá nhiều, phụ huynh sẽ tắt thông báo. Hệ thống cảnh báo sẽ trở thành bù nhìn.

Giải pháp chốt: Dạy Agent cách gửi tín hiệu "Tạm biệt" hợp lệ (Graceful Shutdown) bằng cách bắt sự kiện Power của Windows. Backend chỉ báo động Tím (Bắn Telegram) khi phát hiện mất kết nối ĐỘT NGỘT (Bị kill qua Task Manager).

Bài học 4: Cái bẫy hồi tố (Retroactive Trap)

Sai lầm: Trẻ có thể viết code giả mạo API gửi tín hiệu "Tạm biệt hợp lệ", sau đó tắt Agent và chơi game, lừa được Backend.

Giác ngộ: Dù ở User-mode không thể khóa tay trẻ lúc đó (Prevention), ta có thể bắt quả tang sau (Detection).

Giải pháp chốt: (Cho v2.0) Agent khi khởi động lại sẽ kiểm tra chéo Event Logs của Windows. Nếu không thấy log Sleep/Shutdown tương ứng với tín hiệu "Tạm biệt", nó sẽ báo cáo "Thiết bị bị hack". Kết hợp với "Ngưỡng ngủ tối đa" (Max Sleep Threshold 24h) trên Backend để phòng hờ trẻ tắt Agent vĩnh viễn.

Bài học 5: Ống API "Lẩu thập cẩm" và Nút thắt cổ chai

Sai lầm: Gộp chung Heartbeat (chỉ báo sống), Lệnh điều khiển (Pull), và Log dữ liệu (có thể lên tới vài MB) vào chung một ống API duy nhất (Monolithic Pipe) xử lý theo dạng FIFO (Vào trước ra trước).

Giác ngộ: Nếu mạng chậm, cục Log khổng lồ sẽ làm nghẽn Heartbeat, khiến Backend báo động giả. Tại Backend, việc parse JSON khổng lồ sẽ gây nghẽn I/O Database. Hơn nữa, việc bắt log "Phát hiện Game Cấm" xếp hàng sau 5000 dòng log rác "Di chuyển chuột" là một tư duy phi logic, phá vỡ tính thời gian thực (Real-time).

Giải pháp chốt: Áp dụng Kiến trúc Phân tách Luồng (Decoupled Streams).

  • Luồng 1 (Heartbeat & Command): Gói tin siêu nhỏ (<100 byte), ưu tiên tuyệt đối, chạy mỗi 15s để lấy lệnh khóa máy. Đảm bảo độ trễ thấp nhất.
  • Luồng 2 (Fast-Track Alerts): Khi phát hiện Game Cấm, bắn thẳng API riêng ngay lập tức (vượt đèn đỏ) để phụ huynh nhận Telegram trong 1 giây.
  • Luồng 3 (Bulk Log Upload): Chở log rác, chạy ở Thread ngầm, ưu tiên thấp nhất. Gom đủ 100 dòng mới upload, có rớt cũng không ảnh hưởng luồng điều khiển.

Bài học 6: Nghệ thuật "Chữa cháy" Database MVP

Sai lầm: Lưu hàng triệu dòng Log rác vào bảng PostgreSQL thông thường, và dùng Redis tốn kém chỉ để lưu trạng thái Online/Offline của thiết bị.

Giác ngộ: Lệnh DELETE hàng triệu dòng sẽ sinh ra Dead Tuples làm phình Database và "giết" hiệu năng. Việc dùng Redis ở giai đoạn MVP (dưới 1000 thiết bị) là một sự lãng phí tài nguyên không cần thiết (Over-engineering).

Giải pháp chốt:

  • Phân vùng Log (Table Partitioning): Chia bảng process_logs theo ngày. Xóa log cũ (7 ngày) bằng lệnh DROP TABLE siêu tốc độ, giải phóng ổ cứng lập tức.
  • In-Memory Presence: Lợi dụng việc FastAPI chạy Single Worker ở MVP, lưu trạng thái WebSocket thẳng vào Dictionary trên RAM (Tốc độ đọc ghi mili-giây, miễn phí hoàn toàn).
  • Gom nhóm Ghi ổ cứng (Batching): Chỉ UPDATE trạng thái last_seen_at xuống PostgreSQL mỗi 5 phút một lần để cứu ổ cứng khỏi thảm họa Disk I/O.

Bài học 7: Cuộc chiến Cài đặt (Pairing Flow)

Sai lầm: Nghĩ đến việc dùng Mã 6 số (PIN code) để liên kết thiết bị, hoặc cố gắng xây dựng luồng tự động biên dịch (build) file .exe có nhúng sẵn Token cho mỗi phụ huynh.

Giác ngộ: Mã PIN có thể bị trẻ em nhìn trộm. Việc Build file .exe custom thì quá nặng nề cho server ở giai đoạn MVP.

Giải pháp chốt (Pairing by Login): Dùng cơ chế đăng nhập truyền thống. Agent cài xong sẽ hiện màn hình đăng nhập. Phụ huynh dùng tài khoản Admin cấp để đăng nhập thẳng trên máy con. Backend xác thực, trả về Device_Secret_Token, lưu vào DPAPI. Sau đó màn hình đăng nhập bốc hơi hoàn toàn. Rất bảo mật và vô cùng mượt mà!

Bài học 8: "Bàn tay sắt" Ngoại tuyến (Offline Fail-Closed)

Sai lầm: Cho rằng ghi luật cấm (Rules) xuống local_db.sqlite là đủ an toàn để thực thi khi mất mạng.

Giác ngộ: Nếu trẻ rút Wi-Fi, chúng hoàn toàn có thể dùng tool (SQLite Browser) sửa cột is_banned = FALSE để vô hiệu hóa luật cấm mà Agent không hay biết.

Giải pháp chốt (HMAC Signature): Khi Backend gửi Luật xuống, nó đính kèm một Chữ ký điện tử (HMAC) băm bằng Secret Token của thiết bị đó. Khi Agent đọc SQLite để thi hành luật, nó sẽ tự tính lại HMAC. Nếu chữ ký sai (do trẻ sửa lén file), Agent chuyển sang trạng thái Tự vệ cực đoan (Fail-Closed): Khóa đen toàn bộ màn hình, hiện thông báo "Dữ liệu bị can thiệp trái phép" và chỉ mở lại khi phụ huynh nhập mật khẩu bảo trì.

Đề Xuất Kiến Trúc Truyền Thông 3 Luồng (Decoupled Streams)

1. Mục tiêu Cốt lõi

"Kiến trúc truyền thông này ưu tiên độ trễ lệnh khóa máy dưới 5 giây và cảnh báo vi phạm tức thời, chấp nhận đánh đổi độ phức tạp của việc duy trì kết nối WebSocket hai chiều để đạt được trải nghiệm thời gian thực tuyệt đối và sự an tâm tối đa cho phụ huynh."

Luồng 1: Tuyến Sinh Tử (Heartbeat + Lệnh)

  • Công nghệ: WebSocket hai chiều (Bi-directional).
  • Hoạt động: Agent duy trì kết nối mở vĩnh viễn với Server. Backend chủ động "Push" (Đẩy) lệnh khóa máy xuống. Độ trễ luôn ở mức dưới 5 giây.
  • Cơ chế Reconnect: Áp dụng Exponential Backoff (1s, 2s, 4s...) khi đứt mạng. Ngay khi kết nối lại, Agent gửi sự kiện SYNC_STATE để "kéo" các lệnh bị kẹt.

Luồng 2: Tuyến Báo Động (Cảnh báo khẩn cấp)

  • Công nghệ: HTTP POST (Agent chủ động "Push" cảnh báo).
  • Hoạt động: Khi phát hiện app cấm, nó vượt qua mọi hàng đợi, bắn thẳng API ở một Thread độc lập để Telegram nổ chuông lập tức.
  • Cơ chế Retry: Đưa vào Hàng đợi Ưu tiên (In-memory Queue), lặp lại việc gửi mỗi 3 giây cho đến khi nhận được HTTP 200 OK (At-least-once delivery).

Luồng 3: Tuyến Xe Tải (Log process / Screenshot)

  • Công nghệ: HTTP POST (Batch Upload).
  • Hoạt động: Gom dữ liệu vào SQLite. Mỗi 1-5 phút, Agent đóng gói 50-100 logs thành 1 mẻ đẩy lên Server bằng độ ưu tiên thấp nhất.

Xử lý khi có mạng lại (Offline Recovery)

Hệ thống tuân thủ nghiêm ngặt thứ tự khôi phục sau:

  1. Ưu tiên 1 (Luồng 1): Khôi phục WebSocket & Gửi Heartbeat báo cáo "Tôi đã sống lại" và lấy lệnh bị kẹt.
  2. Ưu tiên 2 (Luồng 2): Đẩy toàn bộ Cảnh báo khẩn cấp lên Server báo cáo "Tội lỗi trong lúc mất mạng".
  3. Ưu tiên 3 (Luồng 3): Batch Upload Log rác để dọn dẹp hiện trường từ từ.

Ràng buộc & Giả định

Việc duy trì WebSocket đòi hỏi Backend (FastAPI) phải tốn thêm tài nguyên RAM/CPU để giữ các kết nối sống (Stateful). Tuy nhiên, vì giả định dự án MVP ở quy mô dưới 1000 thiết bị (CCU), một Server nhỏ hoàn toàn có thể gánh được tải này mà không cần đến kiến trúc Microservices hay Message Broker hạng nặng.
